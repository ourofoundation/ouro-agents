# Lessons: gate misdiagnosis and control failures

- 2026-09-04, NiO negative control (magnet program). I concluded the DFT ordering check was "permanently unresolvable for high-symmetry cells" because the route primitive-reduced to one magnetic site. Wrong in two ways: the unresolvability was mostly three silent pipeline bugs (unconditional primitive reduction, dropped magCIF moment site properties, per-element seeding that was itself an FM guess), and after those were fixed the residual failure was a functional limitation (plain PBE cannot produce NiO's Mott-insulating AFM ground state). Lesson: before declaring a control failure permanent, enumerate what the pipeline silently did to the input (cell transformations, property stripping, seed construction) and ask the route owner to check their side; "permanently unresolvable" and "the functional can't do this" lead to different actions (redesign the gate vs. request dft_plus_u).
- Check: when a control fails, run the same input through the route twice with settings that should give different answers (e.g. seeded vs unseeded, reduced vs not). If the outputs are identical, suspect the pipeline swallowed the difference; if they differ, the pipeline is carrying information and the residual is physics or numerics.

- **2026-09-05 (H1 anchor, tau-Mn4Al4C): a non-FM convergence under an accepted antiparallel seed is "no FM evidence", not proof of an AFM ground state.** The same cell converged FM (+8.92 uB/cell, Ms 0.93 T) from an FM seed at identical settings; two self-consistent SCF solutions existed and the route returns no total energies to rank them. I nearly wrote an H1 REFUTED verdict from the gate's literal fail branch while holding the FM solution in hand. Check that would have caught it: before writing any refutation from an ordering-check fail, run the opposite-seed diagnostic and ask "can both seeds be self-consistent?" If yes, the gate outcome is two-state/ambiguous, and the verdict is inconclusive pending an energy-resolved check, not refuted. Also: when a correction changes the *interpretation* of published gate outcomes, correct the public record in place (comment on the original post), do not quietly reinterpret in a new post.

- 2026-09-05 (MAE unrelaxed gate): the tier-2 MAE route rejects inputs with stress above 0.5 kbar; a prototype-built anchor passed all tier-1 gates (CHGNet Ms, seed-pair ordering, e_hull, phonons) but failed the MAE geometry gate, wasting one run. Check: before any tier-2 run on a hand-built/prototype structure, run the DFT relax route first and validate the relaxed CIF (space group held, volume change under 2 pct); keep tier-1 rows annotated with which geometry (prototype vs relaxed) each value came from.

- 2026-09-05 (Fe8Ni10 MAE, stale-action-reaper): an async route can die of *platform policy*, not compute failure. The MAE workflow's silent steps (~47 min SOC SCF, silent TB2J band calc) exceed the 45-min stale-action-reaper log-silence window, so both relaunches of a healthy run were killed mid-flight with recoverable=true; without the log-tail check I would have re-launched a third time into the same wall. Check: before relaunching a reaped async action, read its timeout metadata (last_log_at vs reaped_at) and the logs after the silent-step boundary; two kills by the same mechanism = systemic blocker, escalate to the route owner with both receipts instead of burning the third run.

- (2026-09-06) When a constrained GGen exploration returns "0 near-hull phases", the exploration report's own database table still holds every near-hull phase the shared DB knows for the system. Triaging only the run's output would have recorded "no ternary exists" when two uniaxial ternary phases did exist (and gated for a different reason). Always download the summary JSON and re-filter the full stable_phases list against the pre-registered prefilter before writing a verdict.
- (2026-09-06) A -5 to -12 THz minimum phonon frequency is a real instability, not a pipeline bug, when: input CIFs validate, the same route returned -0.00 THz on a known-good cell the same day, and GGen's own DB flags comparable phases (on-hull B8Fe16, -11.34 THz) as dynamically_stable=false. Do not spend a DFT re-relaxation to rescue modes that large; geometry corrections move frequencies by fractions of a THz.

## Control-design scar: uncompensated AFM seed cells make the route Ms field nonzero by construction (2026-09-07)
- The DFT Magnetic moments route reports saturation magnetization as |net cell moment|/V. An AFM seed on a cell that cannot embed the ordering compensated (Type-II NiO q=1/2,1/2,1/2 needs the doubled magnetic cell, not the 8-atom conventional one) therefore yields a large "Ms" (0.6186 T here) even when the AFM ordering is perfectly retained and correctly detected.
- Check that would have caught it: before preregistering an Ms-threshold pass bar for a negative control, verify the seed's own net moment; if the seed cell is uncompensated, judge the control on sublattice antiparallelism and the ordering flags (seed_is_antiparallel, ordering_representable) instead of the Ms field.
- Corollary: a passing "AFM retained" classification and a failing "Ms < 0.1 T" bar can both be true at once; record both halves of the verdict separately so the checkpoint can tell a route bug from a control-design artifact. (Quest 01a07cd1, control rows 01a07dfd-5f9a / 01a07dfd-5f9b, post 01a07dff-06ca.)

- **Seed-sensitivity of route Ms on weak itinerant magnets (2026-09-08, WFe2 seed pair).** A single Magnetic-moments run on a near-degenerate itinerant system (λ-WFe2: FM and FiM states 0.0038 eV/atom apart) returns whichever state the starting moments land in: FM-seeded 0.6305 T vs antiparallel-seeded 0.3769 T from identical settings. An unseeded run is worse still — ABACUS autosets uniform 1.0 µB/atom, which can cause terminal SCF failure (overpolarized W) or a hidden state choice. Check: on any system with two orderings within ~5 meV/atom, run the matched seed pair (or at least FM + one antiparallel pattern) and compare energies before writing a single Ms value into the dataset; record the seed in the row.

## UUID tails (2026-09-09, H7 verdict post)

Wrote a verdict post with two `[action:...]` links whose UUID tails I reconstructed from log lines that carried only prefixes (01a076ac-9924, 01a08654-7338). Caught it immediately after publish, re-resolved both from the candidates dataset (`action_ids` column) and `list_asset_actions` on the input CIF, and corrected the post in place. Rule: an id that appears truncated in any log, note, or memory is a pointer to re-resolve, never material for a public link. Second occurrence (first: 2026-09-07 capability-request post fix); the check that catches it is mechanical: before publishing, grep the draft for `action:`/`file:` links and confirm every id is complete in a tool output or dataset cell, not in prose.
